Shenzhen file-share stack · Part 3 of 3

New Box, Same Stack

Both apps are plain Docker Compose services with local bind-mount volumes — no shared database, no cloud storage, nothing else to migrate. Replicating one is copying four things and running one command.

Prerequisite on the new box — Ubuntu with Docker installed:

sudo apt update && sudo apt install -y docker.io docker-compose-plugin
sudo systemctl enable --now docker

fileshare :8080

1 · Copy the folder over
rsync -a ~/fileshare/ newbox:~/fileshare/

Brings the Dockerfile, docker-compose.yml, source, and — since nothing's excluded — the existing files too. Add --exclude shared if you want the new box to start empty.

2 · Build and start
ssh newbox 'cd ~/fileshare && docker compose up -d --build'

Builds from the official python:3.12-alpine image, which pulls normally anywhere — mainland China included.

3 · Rotate credentials, if this is a genuinely separate box

Edit UPLOAD_USER / UPLOAD_PASS in docker-compose.yml before starting — unless you're intentionally standing up a duplicate of the same instance.

4 · Open the port

8080, in whatever firewall or security-group system the new box's host uses.

gokapi :9001

This is the one with a wrinkle — it ships as a third-party Docker Hub image, and that image is exactly what got blocked when we first built this on the Shenzhen box.

Path A

Normal internet access

Outside mainland China, or any network that isn't sitting behind a Docker Hub mirror block.

Skip the Dockerfile entirely — just reference the upstream image:

services:
  gokapi:
    image: f0rc3/gokapi:latest
    container_name: gokapi
    restart: unless-stopped
    ports:
      - "9001:53842"
    volumes:
      - ./data:/app/data
      - ./config:/app/config
ssh newbox 'cd ~/gokapi && docker compose up -d'
Path B

Registry blocked (what we hit)

Mainland China: the daocloud mirror 403s on third-party images, and 163's mirror is dead — its hostname doesn't even resolve.

Download the release from a machine with normal internet — not the blocked box — then transfer it over:

curl -sL -o gokapi.zip \
  https://github.com/Forceu/Gokapi/releases/download/v2.2.4/gokapi-2.2.4_linux-amd64.zip
scp gokapi.zip newbox:~/gokapi/gokapi.zip

Then build a thin wrapper around the raw binary instead of pulling a prebuilt image:

ssh newbox '
cd ~/gokapi
python3 -c "import zipfile; zipfile.ZipFile(\"gokapi.zip\").extractall(\"bin\")"
chmod +x bin/gokapi
cat > Dockerfile <<EOF
FROM alpine:latest
RUN apk add --no-cache ca-certificates
WORKDIR /app
COPY bin/gokapi /app/gokapi
RUN mkdir -p /app/data /app/config
EXPOSE 53842
ENTRYPOINT ["/app/gokapi"]
EOF
docker compose up -d --build'

Carrying over existing data

Two honest options, not a default to feel bad about skipping.

Fresh start

Don't copy data/ or config/ — both apps happily initialize empty. Gokapi will ask you to run /setup again; fileshare needs no setup step at all.

Same files, same links 
rsync -a ~/gokapi/data/ newbox:~/gokapi/data/
rsync -a ~/gokapi/config/ newbox:~/gokapi/config/

Carries over admin credentials and every file too. Do this and you still need one more edit —

Don't forget

If you copied Gokapi's config/ across, its saved ServerUrl still points at the old box's IP — every link it generates will be wrong until you update it. Same one-line fix as an IP change: see Part 1, step 3.

That's the whole migration. No database to export, no cloud storage to reconnect — two folders, two docker compose up calls, one firewall rule per app.
